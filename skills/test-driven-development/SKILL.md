# Test-Driven Development

## Purpose

Use a failing executable example to define observable behavior before implementing it, then make the smallest change that passes.

```text
RED → verify failure → GREEN → verify pass → REFACTOR if useful
```

TDD is a tool for behavior and regression risk, not a tax on every changed file.

## Applicability gate

Use TDD when a task adds, changes, or fixes observable behavior and a test can fail for a realistic defect. Typical cases:

- business rules, calculations, validation, and branching
- parsers, serializers, transformations, and protocol handling
- state transitions, orchestration, retries, concurrency, or caching
- APIs, commands, persistence behavior, security, authorization, or money paths
- bug fixes with a reproducible cause
- refactoring where tests are needed to preserve behavior

Do not force TDD when there is no meaningful red/green behavior cycle:

- human-facing prose or ADR wording
- declarative metadata or configuration with no custom logic
- generated or vendored artifacts
- formatting-only edits
- exact mechanical renames or moves already protected by compiler/search/tooling
- deletion of unreachable code where build and reference checks are the relevant proof
- throwaway diagnostic probes that will not ship

A task marked **TDD not applicable** still needs the smallest relevant verification: parser/schema validation, type-check, build, lint, reference search, snapshot generated by an authoritative tool, or explicit manual inspection. If configuration drives custom runtime behavior, test that behavior rather than declaring configuration exempt.

When uncertain, ask: **What realistic production defect should this test catch?** If the answer is concrete, use TDD. If the only answer is “the text/file changed,” use a more appropriate verification.

## RED — define one behavior

Write the smallest test that demonstrates the desired externally observable result.

Before writing it, name:

1. the production defect that should make it fail
2. the expected value derived independently of the implementation
3. the boundary being exercised

Prefer real code. Mock only slow, nondeterministic, privileged, or external boundaries, and keep the behavior under test real. Read [references/writing-good-tests.md](references/writing-good-tests.md) when adding or changing tests or mocks.

## Verify RED

Run only the new test first and observe it fail for the intended reason.

A useful red state:

- fails rather than crashing from test setup
- reports the missing or incorrect behavior
- would pass after the smallest intended implementation

If it already passes, the behavior exists or the assertion does not discriminate. Fix the test or reassess whether a change is needed.

For a bug fix, the test must reproduce the understood root cause or its observable consequence—not merely encode the proposed patch.

## GREEN — implement minimally

Write the smallest production change that satisfies the test and approved requirements.

Do not add speculative options, abstractions, adjacent refactors, or cases not required by another test. Reuse existing code and platform behavior before adding helpers or dependencies.

## Verify GREEN

Run:

1. the new test
2. focused tests for the changed component
3. any compiler, type, schema, or static checks relevant to the task

If another test fails, resolve the behavior conflict rather than weakening assertions blindly.

## REFACTOR — only while green

After the behavior passes, remove duplication or improve names only when the result is simpler. Keep tests green after each refactor. Skip this step when the code is already clear.

## Good-test rules

- Test one behavior at the appropriate boundary.
- Assert outcomes and meaningful side effects, not implementation details.
- Derive expected values independently from the code under test.
- Avoid tests that only grep source text or freeze intentional wording.
- Do not assert that a mock exists; assert the real component's behavior.
- Keep test-only helpers out of production APIs.
- Prefer one regression test over broad low-value coverage.
- Do not test trivial forwarding, constants, or framework behavior unless your code adds a contract or transformation.

## Existing code without tests

For a behavior change, characterize only the behavior you need to preserve, watch that characterization pass, then add a failing test for the new behavior. Do not attempt to retrofit an entire legacy subsystem before making a focused change.

## Integration with debugging and plans

- `systematic-debugging` establishes the root cause before a bug-fix test is written.
- `writing-plans` decides per task whether TDD is required or not applicable.
- `executing-plans` follows the task's declared test strategy but must challenge an incorrect classification.
- `code-reviewer` checks that tests protect meaningful behavior without demanding tests for changes where TDD is not applicable.

## Definition of done for a TDD task

- [ ] The test names a realistic defect or missing behavior
- [ ] The test was observed failing for the intended reason
- [ ] The smallest implementation made it pass
- [ ] Focused checks pass
- [ ] The test exercises real behavior at the right boundary
- [ ] Refactoring, if any, kept the suite green

## Definition of done when TDD is not applicable

- [ ] The plan or report states why no meaningful red/green cycle exists
- [ ] The smallest relevant non-test verification ran successfully
- [ ] No behavior with material regression risk was left unprotected
